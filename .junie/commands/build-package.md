# Навык `build-package`

Используй эту команду, когда нужно создать самостоятельный пакет, который устанавливается в любой совместимый проект Laravel через Composer. Команда не должна изменять зависимости или бизнес-логику текущего приложения без явного согласования.

## Аргументы

Используй имя пакета в формате `vendor/package` и уточни у пользователя домен, если он не указан:

```text
/build-package vendor/package
```

Перед началом проверь, что целевая директория не содержит существующий пакет. Не перезаписывай файлы без подтверждения.

## Обязательные навыки

Перед реализацией изучи:

- `.ai/skills/laravel-package-tools/SKILL.md` — провайдер пакета, публикуемые ресурсы и install-команда.
- `.ai/skills/architecture-ddd/SKILL.md` — слои Presentation, Application, Domain и Infrastructure.
- `.ai/skills/refactoring-ddd/SKILL.md` — правила DDD/CQRS проекта.
- `.ai/skills/dtos/SKILL.md` — типизированные DTO через `spatie/laravel-data`.
- `.ai/skills/documentation/SKILL.md` — документация, сводка и `removed.txt`.

Если навык недоступен, сообщи об этом и следуй локальным правилам проекта; не подменяй реальную реализацию симуляцией.

## Порядок действий

### 1. Спроектировать контракт пакета

- Определи namespace, минимальную версию PHP/Laravel, публичные классы и конфигурацию.
- Проверь, что пакет не зависит от классов конкретного приложения.
- Определи API домена, команды, обработчики, запросы и интерфейсы репозиториев.

### 2. Создать автономную структуру

Используй стандартную структуру Composer-пакета:

```text
package/
├── composer.json
├── README.md
├── LICENSE
├── config/
├── database/migrations/
├── routes/
├── resources/lang/
├── src/
│   ├── Commands/
│   ├── Application/
│   │   ├── Commands/
│   │   ├── Handlers/
│   │   └── Queries/
│   ├── Domain/
│   │   ├── Models/
│   │   ├── ValueObjects/
│   │   └── Repositories/
│   ├── Infrastructure/
│   │   └── Persistence/
│   ├── Http/
│   │   ├── Controllers/
│   │   └── Requests/
│   └── PackageServiceProvider.php
├── tests/
└── docs/
```

### 3. Подключить `laravel-package-tools`

Создай провайдер, расширяющий `Spatie\LaravelPackageTools\PackageServiceProvider`. В `configurePackage()` обязательно задай `->name()` и объяви только используемые ресурсы через `hasConfigFile()`, `hasMigration()`, `hasRoute()`, `hasCommand()`, `hasTranslations()` и `hasInstallCommand()`.

Install-команда должна быть идемпотентной и публиковать конфигурацию, миграции, ресурсы и регистрировать провайдер только там, где это требуется. Добавь auto-discovery провайдера в `composer.json`.

### 4. Реализовать DDD + CQRS

- Presentation содержит тонкие контроллеры и валидацию.
- Application содержит DTO, Actions, Commands, Handlers и Queries.
- Domain содержит бизнес-правила, модели, Value Objects, события и интерфейсы репозиториев.
- Infrastructure содержит реализации репозиториев, Laravel-провайдеры и внешние интеграции.
- Операции записи проходят через `Command` → `Handler`; чтение выполняется отдельными `Query`-классами.
- Межслойные данные передавай типизированными DTO, а не неименованными массивами.
- Не допускай зависимости Domain от Infrastructure и кода конкретного приложения.

### 5. Добавить тесты и документацию

- Напиши Pest-тесты для основного сценария, отрицательных случаев, install-команды и публичного API.
- Перед завершением проверь код по Laravel best practices: согласуй решение с существующими паттернами, используй тонкие контроллеры, dependency injection, Form Request для валидации, `config()` вместо `env()` вне конфигурации, явные типы и безопасную работу с данными.
- Для Eloquent проверь отсутствие N+1, корректные связи и индексы; для API проверь авторизацию, валидацию входных данных, формат ответов и отсутствие утечки чувствительных данных.
- Для очередей, HTTP-клиентов, кэша и транзакций проверь таймауты, повторяемость, идемпотентность и обработку ошибок согласно назначению компонента.
- Создай `docs/<feature>.md` с архитектурой, установкой, конфигурацией, миграциями и примерами использования.
- Обнови `README.md` пакета и `SUMMARY.md` проекта, если изменение заметно для проекта.
- Зафиксируй новые бизнес-пути в `removed.txt`; ядро и авторизацию туда не добавляй.
- Для API добавь OpenAPI-атрибуты и сгенерируй Swagger-документацию.

### 6. Проверить переносимость

Проверь пакет в чистом Laravel-приложении: установка через Composer, обнаружение провайдера, публикация ресурсов, миграции, команды, маршруты и тесты. Не используй локальные `php`, `composer` или `artisan`: команды PHP/Laravel запускай через Sail согласно правилам проекта.

Перед завершением выполни применимые проверки через Sail:

```bash
./vendor/bin/sail pint --dirty --format agent
./vendor/bin/sail php vendor/bin/phpstan analyse --memory-limit=2G
./vendor/bin/sail test --compact
```

Все три проверки обязательны. `Pint` должен завершиться без незакоммиченных исправлений после форматирования, `PHPStan`/Larastan — без ошибок на максимальном доступном уровне проекта, а Pest — без падений. Нельзя скрывать ошибки добавлением новых исключений в baseline, отключением правил, снижением уровня анализа, пропуском тестов или ослаблением утверждений.

Если пакет содержит JavaScript/TypeScript, дополнительно выполни проверку сборки:

```bash
./vendor/bin/sail npm run build
```

## Критерии готовности

- Пакет устанавливается в чистый Laravel-проект без ссылок на текущий проект.
- `composer.json` содержит корректные `require`, PSR-4 и auto-discovery провайдера.
- Провайдер использует `laravel-package-tools`, а install-команда безопасна при повторном запуске.
- DDD/CQRS-разделение и DTO соблюдены, публичный контракт покрыт тестами.
- Код соответствует Laravel best practices, проходит `Pint` и `PHPStan`/Larastan без подавленных ошибок.
- Все обязательные тесты и, при наличии фронтенда, production-сборка проходят успешно.
- README, документация, `SUMMARY.md` и `removed.txt` обновлены согласно навыку документации.
